# 版本策略

標準協定怎麼升版、什麼算破壞性變更。

## 1. 兩個版本號，不要混淆

| 版本號 | 是什麼 | 形態 | 誰讀它 |
|---|---|---|---|
| **協定版本** | 相容性世代 | 單調遞增整數（`1`、`2`…） | 兩端的程式，用來判斷「我們說的是不是同一種話」 |
| **spec 修訂版** | 這份文件本身改到第幾版 | semver（`info.version`） | 讀文件的人 |

同一個協定版本內，spec 修訂版會前進很多次——補字、補範例、補一個選填欄位。
**協定版本只在相容性斷掉的時候才動。**

## 2. 協定版本應該進得了「精確比較」的位置

協定版本**應**被放進兩端都必須一致的地方（例如認證用的 canonical 字串，
或服務自報身分的 descriptor），讓版本不合**直接失敗**。

替代方案是讓協議不合的兩端「盡量互通」，結果會是一個半通的系統：
多數呼叫成功，少數在意想不到的地方失敗，而且沒有任何一個錯誤訊息會提到版本。
**乾脆地失敗，比悄悄地半通好查太多。**

**應**同時有第二道比對（呼叫端拿到 descriptor 後比對其宣告的協定版本），
這樣就算某天第一道不再涵蓋版本，版本不合仍然會被抓到。

## 3. 什麼算破壞性

| 變更 | 破壞性？ |
|---|---|
| 回應新增欄位 | 否 |
| 請求新增**選填**欄位 | 否 |
| 新增資源／動作 | 否 |
| 列舉新增值，且呼叫端對未知值有退化行為 | 否 |
| 列舉新增值，但呼叫端沒有退化行為 | **是** |
| 移除欄位 | **是** |
| 改欄位型別或語意 | **是** |
| 請求新增**必填**欄位 | **是** |
| 收緊驗證（本來會過的開始不過） | **是** |
| 改端點路徑或方法 | **是** |
| 改簽章涵蓋的內容 | **是** |

判準是**呼叫端的視角**：任何會讓「一個原本正常的呼叫端開始失敗」的變更，
都是破壞性的——即使實作起來只是一行。

## 4. 非破壞性變更怎麼做

1. 改 `<協定>/v<N>/openapi.yaml`。
2. 提高 `info.version` 的 minor（新增）或 patch（文字）。
3. 跑 spec 的 lint。
4. 更新實作；若動到簽章相關的東西，**先改測試向量的正本**，
   再讓每個語言的實作都重現得出新向量。
5. 服務可以照自己的步調採用。**標準協定先改，實作再跟。**

> **註**：反過來做——先在實作裡改形狀、再回頭補規範——就等於讓「規範」
> 變成一份事後追認的文件，而它唯一的價值是**在實作之前**就說得清楚。

## 5. 破壞性變更怎麼做

**不要就地改 `v1`。** 開 `<協定>/v2/`。

```
<協定>/
├── v1/openapi.yaml     ← 保留，直到最後一個實作遷完
└── v2/openapi.yaml     ← 新的
```

過渡期：

1. 開 v2 的 spec，實作內兩個版本並存（例如 `…/v2` 子套件或子路徑進入點）。
2. **呼叫端先支援兩版。** 否則升版就變成一次必須同時完成的全機群停機。
3. 服務逐一遷移，各自宣告自己說哪一版。
4. 最後一個服務遷完後，才移除 v1。

> **註**：如果所有實作都依賴同一個共用 module，升版的實際動作是
> 「各服務把相依指向新的 major 版本」，而不是「各服務同步一份副本」。
> 這讓過渡期的狀態可以直接從相依宣告讀出來——而副本那條路，
> 沒有任何地方讀得出「誰還沒遷」。

### 首個正式版本之前的一次性例外

本節的規則保護的是**已經在線上的呼叫端**。首個正式標籤發布**之前**，
線上不存在任何呼叫端，開 v2 只會讓第一個正式版本從「同時維護兩代」開始——
那是成本，不是相容性。所以那段期間**可**就地接受破壞性變更。

**此例外隨首個標籤失效。** 標籤之後一律走升版路徑；「反正還早」不是理由，
判準是「線上有沒有呼叫端」，而標籤發出之後答案永遠是有。

## 6. 為什麼不用 semver 當協定版本

協定版本是**單調遞增的整數**，不是 `1.2.3`。

因為它要進簽章、也要進服務自報的身分，而這兩處需要的是一個
**可以精確比較相等**的值。semver 的相容性規則（`^1.2.0` 之類）在這裡沒有意義：
兩端要嘛說同一版，要嘛不說——**沒有「相容但不同版」這個狀態。**

spec 文件本身的修訂版由 `info.version` 用 semver 表達，那才是它適合的位置。

## 7. 標準協定要改動時的檢查表

- [ ] 這是破壞性變更嗎？（對照 §3）
- [ ] spec 改了，而且 lint 綠。
- [ ] `info.version` 動了。
- [ ] 每個語言的實作都跟上，測試綠。
- [ ] 動到簽章的話，測試向量的正本更新，且每個語言都重現得出來。
- [ ] 沒有為了實作新協定而拖進新的相依。
- [ ] 提到被改動處的文件一併更新。
