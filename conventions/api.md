# 協定慣例

本文件規範**跨協定**共用的規則。單一協定自身的形狀由其 `openapi.yaml` 定義。
新增端點或欄位前必須先讀本文件。

## 0. 術語與規範關鍵字

### 0.1 術語

| 術語 | 定義 |
|---|---|
| **標準協定** | 一份規範性定義，是所有實作的唯一權威來源。一份標準協定＝一個 `<協定>/v<N>/` 目錄。 |
| **協定版本** | 標準協定的相容性世代，單調遞增整數。見 [`../protocols/versioning.md`](../protocols/versioning.md)。 |
| **實作** | 遵循某標準協定的程式：client library，或某服務內的服務端。 |
| **呼叫端 / 服務端** | 一次協定互動中發出請求的一方 / 接受請求的一方。 |

> **註**：用「標準協定」而不用「契約」——後者聽起來像雙方的約定條款，
> 而這裡定義的是**線路格式**。

### 0.2 規範關鍵字

規範性描述採用 RFC 2119 的語意：

| 中文 | 英文 | 語意 |
|---|---|---|
| **必須** / **不得** | MUST / MUST NOT | 絕對要求。違反即不符合本協定。 |
| **應** / **不宜** | SHOULD / SHOULD NOT | 強烈建議。偏離前必須理解並記錄代價。 |
| **可** | MAY | 選用。實作與否都符合協定。 |

> **註**：三者的差別在**互通性**。「必須」被違反時，另一端會拒絕你或誤解你；
> 「應」被違反時仍然通得過，但你放棄了某個保證（通常是可診斷性或安全邊界）；
> 「可」則純粹是實作的自由。

規範性條文陳述**要求**；理由與背景寫在 `> **註**` 區塊裡。兩者分開，
是為了讓實作者能只讀條文就寫出符合協定的程式。

## 1. 一份協定，一種錯誤形狀

**同一份協定內的錯誤形狀必須一致；不同協定之間不必、也不應強求一致。**

一個協定若實作了已規定錯誤形狀的公開標準（例如 OAuth 2.0 的
`{ "error": "invalid_grant", "error_description": "…" }`，RFC 6749 §5.2），
就**必須**照那份標準，**不得**為了與自家其他協定一致而改寫它。

自訂協定的錯誤形狀由該協定自己定義，並**應**在兩種原型裡選一種：

| 原型 | 形狀 | 什麼時候用 |
|---|---|---|
| **給人讀的** | `{ "error": "…", "fieldErrors": { … } }` | 錯誤最終會被渲染成一段文字，或標在某一格輸入框上 |
| **給程式讀的** | `{ "error": { "code": "…", "message": "…", "request_id": "…", "retryable": bool, "details": { … } } }` | 呼叫端收到後要**當下決定**重試、換一條路、還是往上報 |

偏離時**必須**在協定自己的文件裡登錄，並寫明放棄了什麼。

> **註**：硬把所有協定統一成一種形狀，等於讓實作公開標準的那一份不再符合它——
> 每一個現成的客戶端都會失效。一致性在這裡不是美德，符合各自該符合的規範才是。

### 1.1 為什麼「給程式讀的」需要多兩個欄位

`code` 與 `retryable` 是「給人讀的」形狀表達不了、而程式又**必須**據以分支的：

- **`code`**——穩定、機器可讀的分類。呼叫端據以分支，訊息文字可以隨時改寫；
  拿 `message` 做字串比對的呼叫端，會在下一次改錯字時壞掉。
- **`retryable`**——這次失敗重送有沒有意義。`503`（後端不可用）與
  `409`（唯一性衝突）都是失敗，但一個該退避重試、一個重試一萬次都一樣。

`request_id` 進錯誤信封，是為了讓使用者回報的那個 id 能直接拿去查服務端的日誌。

**代價**：同時接觸兩種原型的呼叫端，`error` 欄位在一邊是字串、在另一邊是物件，
必須依協定分支。之所以接受，是因為替代方案（把 `code` 與 `retryable` 平鋪在
頂層）會讓「這個欄位屬於錯誤還是屬於回應」在每次讀 payload 時都要重新想一次——
而錯誤路徑正是最不該需要思考的那條路徑。

### 1.2 `fieldErrors` 的鍵必須是欄位鍵

```json
{ "error": "至少需要一個 redirect URI",
  "fieldErrors": { "redirect_uris": "至少需要一個 redirect URI" } }
```

鍵**必須**對應該欄位在協定裡的鍵。採用「給程式讀的」形狀時，欄位錯誤放在
`details.field_errors`，規則相同。

> **註**：鍵對不上，前端就只能退回顯示一條橫幅——而那正是 `fieldErrors`
> 要取代的東西。

## 2. 命名

| 場合 | 慣例 | 例 |
|---|---|---|
| JSON 欄位 | 跟著該協定自己的風格：`camelCase` 或 `snake_case` | `fieldErrors`／`next_cursor` |
| 實作公開標準的協定 | **照那份標準**，不論它用哪一種 | `access_token`、`email_verified` |
| 設定鍵 | `<分區>.<欄位>`，小寫 `snake_case` | `session.ttl_hours` |
| 資源 id、動作 id | 小寫 `snake_case` slug | `accounts`、`verify_account` |
| 服務 slug | 小寫，以連字號分隔 | `billing`、`user-directory` |
| 角色 | `<服務 slug>.<角色>` | `billing.admin` |

同一份協定內**必須**維持單一命名風格；**不得**為了跨協定一致而變更任一方。

> **註**：兩種大小寫並存是刻意的。實作 RFC 的那一側，欄位名由 RFC 決定，
> 不是我們的選擇。

### 2.1 角色必須命名空間化

角色名**必須**帶服務 slug 前綴。身分供應者只解讀自己定義的那幾個；
其餘角色一律由**擁有該前綴的服務**解讀。

服務授權時**必須**檢查自己定義的角色，**不得**改為檢查供應者層級的管理員角色。

> **註**：無前綴的 `admin` 在一個有多個服務的平臺上無法回答「他是哪個服務的
> 管理員」。而把平臺管理員當成本服務管理員，會在沒有人決定過的情況下
> 放寬「誰能操作」。

## 3. 分頁

集合列舉**必須**採用游標分頁，**不得**採用 offset 分頁。

```json
{ "rows": [ … ], "next": "eyJvIjoyNX0", "total": 42 }
```

- 游標欄位為空字串或不存在，代表列舉已完整。呼叫端**不得**以「回傳筆數少於
  `limit`」判斷結束。
- 游標**不透明**：呼叫端**不得**解析或構造它；服務端**可**隨時變更其編碼。
- 總數欄位為選用。服務**可**省略（不給或給 0）。

**規範的是語意，不是欄位名。** `rows`／`next`／`total` 與
`items`／`next_cursor` 都合規——依 §2，命名風格跟著各自的協定走。

> **註**：伺服器有權回得比你要的少，所以「筆數少於 limit」不是結束訊號。
> 總數選用，是因為有些集合算總數比列一頁還貴——強制提供只會讓服務去猜。
>
> 「MUST 到哪為止」值得講明白：換掉 offset 會讓深頁掃描與併發插入下的漏列
> 變成兩種不同的故障，那是真的互通性問題；`next` 或 `next_cursor` 則只是
> 一個名字。把名字也寫成 MUST，只會逼某一份協定在自己通篇的風格裡夾一個
> 例外——而 §2 已經說過那種例外會被下一個人當成筆誤修掉。

## 4. 密鑰欄位唯寫

對任何 `type: secret` 的欄位：

- `GET` **不得**回傳明文。已設定**應**回傳 `"••••••••"`，未設定**應**回傳 `""`。
- `PUT` 收到空字串，**必須**解讀為「不變更」，**不得**解讀為「清空」。
- `PUT` 收到與遮罩值相同的字串，**必須**解讀為「不變更」。

清空密鑰**必須**由一個獨立的、標記 `danger` 的動作提供。

> **註**：第三條看起來多餘，但少了它，「打開表單、什麼都沒改、按儲存」
> 就會把密鑰覆寫成一排圓點。

## 5. 缺席即不變更

§4 的一般化：部分更新中**缺席的欄位一律代表「不變更」**，任何實作
**不得**把缺席解讀為「清空」。

具清除語意的操作**必須**實作為明確的、標記 `danger` 的動作。

> **註**：只想改一個角色的部分更新，不該默默把某人的指派全部收走——
> 而那種事故在稽核紀錄裡看起來與正常操作一模一樣。

## 6. 相容性

### 6.1 相容的變更

- 回應新增欄位。
- 請求新增選用欄位。
- 新增資源或動作。
- 列舉新增值——**僅當**協定已為該列舉定義未知值的退化行為時。

### 6.2 破壞性的變更

- 移除欄位、變更欄位型別、變更欄位語意。
- 請求新增必填欄位。
- 收緊驗證規則。
- 列舉新增值，而協定未定義未知值的退化行為。

破壞性變更**必須**依 [`../protocols/versioning.md`](../protocols/versioning.md) §5
走升版路徑，**不得**就地修改既有版本。

### 6.3 未知輸入的處置

- 呼叫端**必須**容忍未知欄位與未知列舉值，**不得**因此失敗。
- 服務端**必須**忽略未知設定鍵與唯讀欄位，**不得**因此拒絕整批請求。

> **註**：把「不認得的型別退化成唯讀文字框」寫進協定，新增型別就不是破壞性
> 變更。反過來說，一個「多一個欄位就壞掉」的呼叫端，會讓服務端永遠不敢加欄位。

## 7. 錯誤訊息必須可據以行動

面向操作者的錯誤訊息**必須**指出具體的設定項與應採取的動作，
**不得**僅陳述失敗。

符合本節的範例：

> 對方拒絕了本次簽章，但兩端時鐘是同步的——所以是共享密鑰或金鑰 id 不一致。
> 請重新輸入與對方設定檔中該鍵逐字相同的字串。

> **註**：「設定有誤」沒有人能照做。

## 8. 對外含糊者必須對內明確

若協定為了安全而對呼叫端隱藏失敗原因（例如對多種驗證失敗一律回
`unauthorized`，以免成為列舉有效金鑰 id 的預言機），則該協定**必須**同時
規定一條對內的診斷路徑，把完整原因交給**已持有密鑰的那一側**。

> **註**：少了後半，前半就只是製造了一個兩端都查不出原因的故障——
> 而那是整套系統裡最難查的一類。

## 9. 限速施加於回報，不施加於拒絕

當協定要求把失敗寫入日誌或稽核時：

- 每一個失敗的請求**必須**各自收到其錯誤回應。
- 回報**必須**限速，且**必須**附上該期間內被折疊的筆數。

所以：**限速的是回報，不是拒絕**。每個請求仍各自收到 401，只是回報被折疊，
並帶著「這段期間還有幾筆」的計數——「這一分鐘還有 31 次」與「就這一次」
是「設定錯了」與「有人在逐一嘗試」的差別。

## 10. 時點數據：過了就取不回來的，當下就要記

有一類數據**只在某一刻存在**：帳號建立的那一刻、信箱通過驗證的那一刻。
它的特徵是——**沒在當下寫下來，日後從任何地方都推不回來**。所以判斷
「要不要記」時，問的不是「現在用得到嗎」，而是**「以後有沒有可能用到」**：
現在用不到但以後可能要，就記；因為補記這件事本身不存在。

三種最常見的漏法，設計新欄位時逐條對照：

| 漏法 | 症狀 | 該怎麼寫 |
|---|---|---|
| 只存布林值 | `verified` / `disabled` / `claimed` 只答「是不是」，不答「何時」 | 布林值旁邊配一個 `*_at` |
| 只存 `last_*` | `last_login_at` 每次登入覆寫，第一次的時點永久消失 | 需要首次語意時另存 `first_*_at` |
| 集合成員沒有時間 | JSON 陣列裡的項目只有身分，沒有取得時間 | 項目本身帶 `*_at` |

反過來，**可以從保留中的資料回推的就不必存**：能由既有紀錄算出來的峰值、
能從稽核事件回溯的來源，都不是缺口。只有稽核本身會被清理時，才需要另存。

### 補上這種欄位時，舊資料留空

既有資料列沒有那個時點，因為那一刻確實沒被記下來。**留空**——
不要拿相近的欄位（`created_at`）去充當 `verified_at`。
缺值誠實地說「不知道」；充數的值會被當成事實讀，而且再也分不出哪些是真的。

所以這類欄位在協定裡一律**選填**，呼叫端必須能處理它不存在。
