# hoshi-standards

Hoshivel 對外開放的**工程規範**：協定慣例與版本策略。

| 文件 | 規範什麼 |
|---|---|
| [`conventions/api.md`](conventions/api.md) | 跨協定共用的規則：錯誤形狀、命名、分頁、密鑰欄位、相容性、時點數據 |
| [`protocols/versioning.md`](protocols/versioning.md) | 標準協定怎麼升版、什麼算破壞性變更 |

實作在 [hoshi-sdk](https://github.com/Hoshivel/hoshi-sdk)。判準是一句話——
**被 import 的**進 hoshi-sdk，**被遵守的**進這裡。

## 這兩份文件是給誰的

它們是從 Hoshivel 內部的工程規範裡挑出來的**通用部分**。挑選的判準是
「這一條換到別人的系統還成立嗎」——成立的在這裡，只對某一套服務拓撲成立的
不在。所以這個倉庫刻意很薄：**薄是判定的結果，不是還沒寫完。**

規範關鍵字（必須／不得／應／不宜／可）依 RFC 2119 使用，語意見
[`conventions/api.md`](conventions/api.md) §0.2。條文陳述**要求**，
理由與背景寫在 `> **註**` 區塊——兩者分開，是為了讓實作者能只讀條文
就寫出符合協定的程式。

## 為什麼規範要跟實作分開放

一條寫在某個服務原始碼註解裡的規則，其他服務不會知道。下次有人在別的服務
做同一件事，就會做出第二種版本——然後沒有人知道哪一份是對的。

這個組織被那個形狀咬過幾次，所以規則有一個唯一的正本，而實作是它的下游。
順序永遠是**規範先改，實作再跟**。
